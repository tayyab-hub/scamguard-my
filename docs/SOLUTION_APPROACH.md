# Solution approach

SCAMGUARD implements an authenticated decision-support workflow around distinct analysis methods. The related-system comparison shows why collecting different signals does not make those signals interchangeable. A common interface therefore standardises the presentation of evidence and uncertainty while preserving each method's meaning.

The browser renders React components written in strict TypeScript. React Router separates public account/help routes from protected application routes. TanStack Query manages server state and invalidation; Zod validates responses at the transport boundary. Frontend visibility supports navigation, while FastAPI enforces authentication and ownership. Vercel serves the built application and rewrites `/api/v1` to Render. The API uses SQLAlchemy/Psycopg to transact with Neon PostgreSQL. Alembic records schema evolution explicitly. Figure 1 shows the deployment and trust boundaries; Figure 2 shows data retention.

Message analysis uses a checksum-verified JSON TF-IDF Logistic Regression artifact with LEGITIMATE, SPAM and SCAM labels. Contextual rules identify supported indicators, and Message fusion preserves conservative evidence floors. URL analysis is a separate learned random forest over 27 locally derived string features with its own rules and fusion policy. It does not visit destinations, obtain TLS certificates or query live reputation. Phone analysis uses pinned numbering metadata and deterministic policy; valid numbers do not establish a trustworthy subscriber. QR decoding classifies the payload and routes supported content to an existing engine. Generic payment TLV/CRC checks describe a structural subset and byte consistency, not merchant legitimacy.

The interface displays categorical risk separately from confidence. The Message display converts the stored score to points out of 100; the URL display maps ordinal categories to 0/33/67/100. Neither is a calibrated fraud probability, and scores are not comparable across modalities. Insufficient Evidence remains distinct from Low. Completed records preserve evidence, method versions and timestamps; Analyse again creates a new assessment rather than editing the old one.

Passwords use Argon2id with time cost 3, 65,536 KiB memory and parallelism 2. The database stores password hashes and HMAC digests of opaque session/reset tokens. The cookie is HttpOnly and Secure in production. Exact Origin and synchronizer CSRF checks protect authenticated mutations and private search. Owner identity comes from the validated session and is applied to every private query. These controls align with relevant password-storage and CSRF guidance, without establishing comprehensive security certification (OWASP Foundation, n.d.-a, n.d.-b).

Uploaded QR images are byte/pixel/dimension bounded, decoded in memory and discarded. Live camera frames remain on-device; detection stops the stream and presents inert text before a separate Analyse action. Task 9 redacts first-field Wi-Fi passwords and HTTP(S) userinfo embedded in payment payloads before saving new records. Original decoded bytes are used for assessment, so the stored redacted payment text is not a reusable payment instruction. Figures 4 and 5 explain the authentication and QR lifecycles.

Optional external AI review is implemented behind backend configuration and is disabled by default and in the reported evaluation. It can only provide bounded grounded context for eligible ambiguous messages; it is not required for the local workflow. Provider failures preserve local results. No application, methodology or production configuration change was made for this academic pass.
